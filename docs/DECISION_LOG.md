## How to update this log

Add a new decision when a business rule, source boundary, workflow, schema boundary, or irreversible technical choice changes. Do not edit history to make an old decision look current: mark it Superseded and add the replacement ID. Link implementation work and requirement IDs in the commit or pull request.

### D066 — Permanent Part identity, generated names and advisory sharing scope (implemented by D069)

Accepted by the owner on 6 October 2026; implemented in the Grist-backed slice recorded as D069 on 7 October. Part number follows the discussed SM-P-000001 central sequence and is independent of name/scope/revision. Generate the name from the selected Global/Product/Product Model/Model Code shortcode, user-entered description and meaningful variant when needed. Sharing scope is for naming/advisory warnings; it must not restrict Model Code configuration or automatically assign descendant codes. Several chassis designs can share Model scope with different names/numbers and code subsets. Scope/name changes retain identity, number, engineering revision and references, while recording separate immutable metadata history and aliases.

This decision superseded the name-derived identity approach behind the 5 October Part creation slice, while preserving D065 source provenance, normalization, audit and retry rules. The identity/naming prerequisite is implemented by D069; the separate import/configuration gates remain open. See [PART-002 specification](PART_IDENTITY_REQUIREMENTS.md) for acceptance cases and migration requirements.

### D067 — Part engineering revisions require the CR process

Accepted by the owner on 6 October 2026. All managed Parts remain Rev A until the CR flow is implemented. A Part engineering revision means the Part followed that flow; future Rev B or later requires the corresponding approved CR and retained approval/design evidence. Mapping, refresh, reuse, naming and scope changes cannot automatically revise the engineering definition. Name/scope metadata versions remain separate audit history and never imply CR approval. This constrains the future-revision language in PART-002/D066; see PART_IDENTITY_REQUIREMENTS.md.

### D069 — Grist is canonical for Part business records

Accepted and implemented 7 October 2026 for PART-002/D066, PART-003/D067 and the 7 October purchased-Part clarification. Extend the established `ProductPart` master and persist Part identity/number, generated names and metadata history, aliases, shortcodes, explicit Rev A, source mappings, line/component/drawing composition, purchase specifications, reviewed vendor equivalences, actual purchase history and selected-rate evidence in the validated Safari Manufacturing Grist document. Do not publish managed Part business data only to SQLite. The local SQLite file coordinates the one explicitly bound writer host, reserves monotonically increasing numbers, serializes its processes and journals retry/recovery fingerprints; do not support independent host allocators or automatic takeover.

Schema `safari-parts-grist-2026-10-07.v8` was applied additively after a native backup passed SHA-256 and SQLite integrity checks. Legacy ProductPart rows, numeric PartRevision evidence and LineMaster ownership are retained unchanged pending reviewed classification. Part creation and writes require Grist readback/recovery and the same request key after a lost response. Production carries a coordinator binding but no fabricated managed Part or purchase records. Synthetic persistence tests use a temporary isolated Grist document.

For purchased costing, select the newest eligible posted/completed actual purchase by transaction timestamp across reviewed vendor mappings for one canonical Part specification/revision. Exclude quotes, drafts, voids, returns/reversals; deduplicate identical transaction lines; block conflicting duplicates and differing rates tied at the latest timestamp. Applied unit rate is net merchandise less explicit discount, excluding tax, freight and other charges. Currency and UOM require explicit approved conversion evidence. An incomparable newest purchase, ambiguity or no history is unavailable/review-needed, not zero or an older-rate fallback. Persist historical selection evidence; keep MaterialRateLog/default behavior separate.

Explicit per-Code costing configuration/Summary integration, approved CR revisions beyond A, and legacy identity migration remain later gates. See the implementation status in `PARTS_ENTITY_DIAGRAM.md` and `PARTS_GRIST_COMPLETION_PROMPT.md`.
