# Spares master and Model Code Issue Slip requirements — draft

Recorded from the owner's 17 November 2026 requirements. This document separates requested behavior from proposed design and unresolved choices. It is not an implementation assignment or approval of the proposals below.

## Owner requirements

**S1 — Issue Slip selection:** Import Issue Slip numbers and their entries as entered in the selected ODS. Within a selected Product Model Code configuration, let the user choose the relevant Issue Slip numbers, then include/exclude individual entries. Preserve selections independently for each configuration. The user can add/remove spare Item Code references from that configuration. Do not infer Model Code applicability merely from a shared workbook or description.

**S2 — Source lineage:** SparesDB in the product ODS is a local cache originating from Template DB/Spares List - Master.ods. It contains purchased and in-house items whose Item Code string does not reliably identify sourcing type. Preserve source workbook/sheet/row, formulas versus cached values, observed version/hash and original Item Codes. Existing Spares Detail and Spares Summary entries must seed the migration of existing spare compositions, with review of unresolved references.

**S3 — Shared spares master:** Provide a canonical SparesPartsCode master for purchased and in-house spare items, including creation, modification, costing and maintained selling prices. A spare composition can reference a whole canonical Part, selected manufacturing line items, another spare code, or a combination. Preserve quantities/units and the original workbook's quantity override behavior. References must resolve to canonical identities, not mutable spreadsheet row positions. Reuse existing Part/line/purchase/configuration responsibilities rather than introducing a second conflicting engineering or rate authority.

**S4 — Dependency propagation:** Changes to saved Part mappings/linked Parts must be reflected automatically in spare codes using those Parts, including their currently accepted spare definitions, without a separate manual acceptance step for every dependent spare. Owner explicitly selected this behavior on 17 November 2026. Maintain dependency/where-used visibility and propagate changes and recalculation through nested spares. Record new accepted spare versions automatically with cause, source version and before/after evidence rather than rewriting prior accepted versions or saved monetary snapshots. This supersedes the proposed manual spare-review gate, not the engineering controls on the underlying canonical Parts. Unsaved UI drafts are not committed source changes. Circular spare composition must be rejected and a whole Part plus its included lines must not silently charge the same occurrence twice. If a dependency is missing, ambiguous, cyclic or cannot be costed, surface the affected spare as unresolved rather than publishing a fabricated complete cost.

**S5 — Numbering and compatibility:** Establish maintainable new numbering/coding while retaining legacy Item Code references and lookup. Purchased/in-house classification must be explicit and editable through a governed change, not inferred from the identifier. Resolve conflicting imported legacy identities rather than silently merging items.

**S6 — Per-item selling-price policy:** Owner requires a selectable pricing method for each spare item. Default every item to 40% above cost (cost multiplied by1.40). Allow percentage markup above cost, fixed amount above cost, fixed selling amount independent of cost, and a rule based on another code's selling price. Keep the selected policy/parameters and effective price history per item. A fixed selling amount stays fixed when cost changes; cost-based policies recalculate with their cost dependencies. Selling-price dependencies between codes require cycle detection separately from component-cost composition. Do not substitute another item's selling price for component cost merely because the selling-price policy references it. Markup and margin must be labelled distinctly; a40% markup above cost is not a40% margin on selling price. The exact adjustment options for another-code SP remain open below.

**S7 — Authoritative persistence and cost aging:** Owner requires all saved business facts in Grist, not a UI-local business database. Reuse existing Grist Part mappings/baselines and technical-only local coordination/recovery. Spare cost breakdowns must expose source cost dates/aging for purchased items and each material/process input; automatic Part/spare recalculation must not reset the age of unchanged source costs. See B9/B10 in NEXT_IMPLEMENTATION_BACKLOG_2026_11_17.md for shared persistence, date provenance, aggregate-age and historical snapshot requirements. Cost aging is requested work, not claimed to be fully implemented already.

## Proposed design, not yet confirmed

- One neutral permanent code sequence, for example SM-S-000001, with purchased/in-house type as a separate field. Maintain legacy codes such as S1KX011 as searchable aliases with source provenance. Avoid changing the identifier when sourcing changes.
- Model Code configuration editor: select Issue Slip numbers, show source entries and reasons for excluded/overridden rows, include/exclude entries and add/remove spare references. Edits here affect that configuration, not the shared source slip or another code. Retain ODS NO state as source evidence and make any configuration override explicit.
- Spare master editor: identity/type/legacy codes; composition using whole Parts, selected canonical lines and nested spare codes; live cost and weight breakdown; selling price/history; where-used and pending change indicators. Whole-Part and selected-line references need distinct dependency semantics: whole-Part membership can follow approved Part changes, while explicitly selected lines retain their own stable identities.
- A removed configuration entry removes that link. Retiring a used master code preserves historical references; destructive deletion of used masters is not assumed.
- A live calculation can update from current eligible rates; saved monetary snapshots remain frozen. Underlying Part engineering changes retain their existing accepted-baseline/RevA/CR safeguards. Accepted spare definitions automatically version/propagate as directed by S4. Distinguish imported source cost, calculated in-house cost and selling price; never use the sale price as the component cost by default.
- Preserve the Stores freight/handling policy as explicit source evidence and cost categories; do not silently generalize it to every spare or double-charge costs already included in a source contribution.

## Confirmed owner decisions — 17 November 2026

1. Automatically revise accepted spare definitions too. No separate manual review is required for each dependent spare. Preserve the historical versions and frozen saved cost facts; make the changed current accepted definition explicit.
2. Configure pricing per item using the owner's selectable modes: percentage of/above cost, amount above cost, fixed amount, or based on another code's SP. Default40% above cost for all items. Existing imported selling prices remain historical/source evidence; the default policy must not silently overwrite them during requirements capture or an unapproved import.

## Linked selling-price decision — confirmed 17 November 2026

Owner confirmed that pricing based on another spare code's selling price must support percentage or fixed-amount adjustments, not just an exact match. Provide an explicit adjustment method: percentage relative to the linked selling price, or a fixed amount relative to it. A zero adjustment gives an exact match. Positive/negative adjustments represent increases/decreases; keep the adjustment and resulting price visible. Link to the stable spare identity, propagate changes through dependent current prices, and reject self-reference/circular selling-price dependencies. Missing/invalid upstream prices must remain unavailable rather than silently becoming zero. Historical saved prices/snapshots remain frozen.

Do not assume that selecting a cost percentage means selling at40% of cost: the owner's explicit default is40% ABOVE cost. A separate margin-on-selling-price mode, tax basis and rounding policy have not yet been specified. Percentage and fixed-amount adjustment are separate methods; combining both in a single linked-price rule has not been requested.

The linked-price clarification is resolved. Agree the import/editor implementation scope and acceptance criteria before assignment. No new PR, application implementation, production data/schema changes, source workbook writes or implementation dispatch were performed for this requirements capture.
